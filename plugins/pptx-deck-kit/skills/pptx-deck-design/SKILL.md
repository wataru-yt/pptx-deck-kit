# pptx 資料のデザイン

資料は、伝える論旨に必要な情報を組み立ててから図にする。手元の原稿にある数値から図を決めない（`references/argument-and-evidence.md`）。

分かりやすさは装飾ではなく、視線の行き先を1つに決めることで作る。各ページを「短いタイトル → 結論のリード → 1つにまとめた図」の3層に固定し、図の中の強調を1か所に絞り、残りは灰色・細線・小さい文字で退かせる。表は、見出しの下の線1本・行の間の薄い細線・余白で組み、行に背景色を敷かない。流れや段階の図の構造は、薄い塗りブロックと白い溝で見せる。説明は図の下に足さず、指す要素の隣に短く置く。同じ図はページをまたいで同じ座標で描き、めくったときに差分だけが動くようにする。

**REQUIRED SUB-SKILL:** 生成・差分確認・バックアップ・本番反映は pptx-build-sync の手順に従う。このスキルは各ページの見せ方と描き方を担う。

## 作り始める前に（必ず最初に）：見た目の設定を確かめる

資料を作り始める前に、個人の `~/.claude/pptx-deck/theme.json` とプロジェクトの `.claude/pptx-deck/theme.json`（作業フォルダから上へ探す）があるかを確かめる。

- **どちらも無く、質問のツール（AskUserQuestion）が使えるなら、論旨や build.js より先に、利用者に1回だけ聞く**（theme スキル `/pptx-deck-kit:theme` の「A」）：「資料の見た目（色・ロゴ・フッター）はどうしますか？ ① 会社のテンプレート（pptx）がある ② 会社の色とロゴだけ決める ③ おまかせ（題材に合わせて毎回選ぶ）」。答えを待ってから作り始める
- `mode: "auto"` のファイルがあるとき、利用者が「おまかせで」「今回はそのまま」と言ったときは、聞かずに題材で色を選ぶ（決まり13）
- **質問のツールが使えないときは、聞かない。** 非対話の実行（`claude -p` など）には AskUserQuestion が無い。文章で質問して返答を待つと、そこで終わって資料ができない。聞かずにおまかせで進め、最後の返答で「見た目は `/pptx-deck-kit:theme` で会社の色やロゴに変えられる」と一言添える

## 最優先の規則：1ページ1メッセージ、ベースの図は1つ、密度は図の中で作るこのスキルの他の記述と衝突したら、この節を優先する。

1. **メッセージは1ページに1つ。** タイトルとリードは、その1つだけを言う。2つ言いたくなったら、図を足さずにページを分ける。同じ図で言うなら、同じ図を敷いた続きのページにする（`series`。了承は要らない）。論点そのものを足す・削る分割だけ、提案して了承を取る
2. **構造は1つ。** ガントならガントだけ、樹形図なら樹形図だけ、折れ線なら折れ線だけ、表なら表だけ。別の形式の図を同じページに足さない
3. **ベースの図は、持ち帰る1つがいちばん大きく見えるように描く。** 図は読みやすい密度で描き、余白は残してよい（本文の領域を埋めるために、棒を太くしたり、間を広げたり、中身を引き伸ばしたりしない）。持ち帰る1つ（語か数値）は、図の横に大きく置いてよい。置かないのは、図と関係の無い説明欄・サイド欄、まとめの帯、数値カードの列（KPI タイル）、別の小さな図
4. **情報は、対象のすぐ隣に書く。** 数値・条件・根拠を、対象の線・点・棒の端・セルのすぐ隣に、注釈として図の中へ書き込む。原稿の「示唆」「示すこと」は、帯や説明文として描かず、リードと見る所を決めるのに使う（言い回しは写さない。決まり11）（ノートに移すだけで画面から消さない）
5. **情報の種類を増やして密度を作らない。** 図の種類、別の論点、観点の違う話を足すことは、密度を上げることではない
6. **見やすくするためにデータを図から抜かない。** スピーカーノートや付録へ移してよいのは、そのメッセージに要らない情報だけ。読みやすさは、主役を濃く大きくし、残りを灰・細線・小さい文字で退かせて作る
7. **汎用的な図解を使う。** 業界や資料を問わず広く使われ、説明なしで読み方が共有されている図で描く（一覧は `references/review-checklist.md` の評価基準）。その資料のために考案した図（横長の楕円、階段に社名を載せた図、同じ形の帯・ブロックの列）は使わない。例外は、全体の仕組みを俯瞰するページ（下の「形・ページ分け・見る所・アイコンの決まり」の6）
8. **AI の採点の点数を目的に形式を変えない。** 2026-11-09、AI の視覚採点が 3.4 → 3.8 に上がった版を、依頼者は「悪化した」と評価した。資料の評価は `references/review-checklist.md` の評価基準で行い、AI は図の一覧との照合と、崩れや誤読の発見までを担う。形式の良し悪しの最終判断は依頼者の評価と見本で決める

左右2ペインと `messageBox` の扱い: 同じ観点の2つを並べる比較は、1つの比較の構造として認める。`messageBox` は、図の上に置いて要素を指す注釈としてだけ使い、図の外の説明欄にしない。

## 形・ページ分け・見る所・アイコンの決まり（2026-11-24）

「1ページ1メッセージ」「強調は1か所」は、決まりに書くだけでは守られず、表の1列を丸ごと囲むなどで形だけ満たしていた。そこで、どの決まりも「build.js に書く宣言」と「書いていなければ出る警告」の組にした。警告を消すために宣言だけ足さない。宣言と画像が合っているかを、点検で確かめる。

1. **1つの形は、1つの資料の中で1つの意味にだけ使う。** 課題のページと解決策のページを同じ矢羽と行の表で描くと、別の話に見えない。同じ形を2回使ってよいのは、同じ図そのものをもう一度出すときだけ。build.js の先頭に「形の割り当て」（どの形を何に使うか）を書く。構造の図の部品を別の中身でもう一度呼ぶと、`deck-parts.js` が警告する。同じ意味で中身だけ違う図（月ごとの同じ表など）は、引数の `fig` に同じ名前を書く
2. **1つの図で2つ以上を言うときは、同じ図を敷いた続きのページに分ける。** 1枚目は図だけ。2枚目からは同じ図を薄く敷き、指す所だけ元の濃さで残して（`spot`・`only`）、前面にメッセージボックスを1つ置く。`series` を使うと、図を1回書くだけで、言うことの数だけページが出る。続きのページは離れていてもよい（ロードマップの図を、後ろの資金調達のページでもう一度敷く）。この分け方は中身を変えないので、了承は要らない
3. **全ページで「見る所」を1つ宣言し、そこだけを濃くする。** `base` の `focus`（`series` のページも同じ）に、最初に目が行くべき要素を1つ書く。見る所は、リードの主語か数値に当たる要素1つ。表の列や行の丸ごとは、見る所にならない（表では決め手のセル1つを `focus: true` にする。列の枠は、どの案を選ぶかが主張の評価表だけ）。`focus: false` は、リードが主張を言わないページ（アジェンダ・付録）だけ。主張を言うリードがあるのに `false` にすると、部品が警告する。列挙のページでも、リードが名指しする1つを見る所にする。書き出すと `<資料名>.focus.md` に一覧が出るので、点検で画像と引き比べる
4. **形は、持ち帰る1つがいちばん大きく見えるものを選ぶ（決まり25）。** 伝えたい1文の動詞は、候補を挙げる手がかり：「比べる」は表、「順に進む」は流れ、「受け渡す」はスイムレーン、「回る」は循環、「誰が誰に何を渡す」は主体と矢印の図（`bizModel`）。原稿が2つを対比して書いてあっても、言いたいのが全体の構造なら、比較の表にしない
5. **外部の製品・会社を図に出すときは、公式のアイコンを取得して組み込む。** Slack・Excel・Claude のような製品や、会社を、図の要素（主体、列の見出し、工程で使うアプリ）として出すときは、名前の横にアイコンを置く。手元の `icons/` に無ければ、公式のサイト・公式のブランド素材・手元に入っているアプリから取得する（`scripts/fetch_icon.py`。出どころを `icons/SOURCES.md` に残す）。似た形を自分で描かない。題とリードの文に名前が出るだけなら要らない。図の中に名前があるのにアイコンが無いと、`deck-parts.js` が警告する。外に配る資料では、各社のロゴの使い方の決まりを確かめる
6. **全体の仕組みを俯瞰するページは、部品に無い形でも、中身に合わせたインフォグラフィックを描いてよい。** 部品（テンプレート）の構造に、中身を合わせない。仕組みの全体像を、行と列の表に詰めると、何がどこへ流れるかが形に出ない。元になる絵（動画の場面、手描きの図、既存の資料）があれば、その形を写す。描くときの条件: ベースの図は1つ、見る所を1つ宣言する、外部の製品は公式のアイコン、図を描く関数を1つにして続きのページでも同じ関数で敷く（かたまりごとの矩形を戻り値で返し、`spot` で指せるようにする）、本文の領域（y 2.2〜6.6）に収める。比べる・推移・内訳のように読み方の決まった内容は、これまでどおり部品の定番の図で描く。**自作の図でも、形は定番から選ぶ。** 自分で考えた見せ方（位置を道に置く、など）は、読み手が読み方を知らないので伝わらない。前と後の違いを言うなら Before / After の2列（左右に同じ段を同じ位置で並べ、違う段だけ強調する。無い段は破線の空き枠で見せる）、順に進むなら流れ、関係なら主体と矢印、のように、説明なしで読み方が分かる形にする。俯瞰のページに限らず、同じ内容の図が、元になる素材にあれば、その形を使う。素材の図を先に見てから、部品を選ぶ（ロードマップを段階×観点の表にせず、素材と同じ「駅を進む道と、駅ごとの条件、資金の帯」で描く）
7. **タイトルは「いまどの話か」の項目名だけにする。** 名詞で、全角14字まで（「課題」「解決策」「ビジネスモデル」）。主張はリードの1文に書く。「：」や読点で要点を足さない。タイトルは、そのページの項目名にする（「購入者の内訳」「購入者の不満」「リスクと対策」）。同じ章に別の話のページが続くとき、章の名前を題に並べない（「勝機」が6枚続くと、どのページか分からない）。題の上に章の名前を小さく出さない（部品は出さない。`base` の `section` は警告）。今どの章の話かは、アジェンダと題で分かる。同じ図の続きのページ（series）だけは、同じ題でよい。話しながら見せる資料（ピッチ、発表）の作法。送って読ませる報告書で、タイトルに結論の1文を書く形（アクションタイトル）にするなら、リードを置かない。どちらでも、主張を書く場所は1か所。`deck-parts.js` は、タイトルに「：」や読点があるとき、14字を超えたとき、アジェンダの項目名と違うときに警告する
    - **言葉の選び方（題・アジェンダの項目名・図の中の名前に当てる。2026-11-28）：**
      - 日本の会議資料で普通に使う言葉にする。基準は「日本のビジネスパーソンが会議でこう言うか」。造語、直訳調、その資料だけの言い回しにしない
      - 聴講者が知っている経営の言葉は使う（ターゲット、支払意向額、参入障壁、勝機）
      - 題と名前にも、リードと同じ「聴講者が疑問を持たない」の問い（何の？ どれ？）を当てる。「まとめ」「分析」「方針」「計画」「課題」のような言葉には、何についてかを付ける（×「分析のまとめ」→ ○「顧客・競合分析のまとめ」）。同じ章の中で何の話か明らかなときは、短いままでよい
      - 構成（原稿）の言葉が一般的でなければ、意味を変えずに一般的な言葉に言い換えてよい（題は構成の項目名のままでなくてよい）。アジェンダの項目名と各ページの題は、言い換えた後の言葉でそろえる。言い換えた所は、最後の返答で「前 → 後」で知らせる
      - 例：見方を重ねる → 顧客・競合分析のまとめ／狙う所 → ターゲットと商品案／確かめ方 → 試験販売の計画／払ってよい額 → 支払意向額／勝てる所 → 勝機／難しさ → 参入障壁
      - 自然な言葉かは機械で判定できないので、警告は出ない。`<資料名>.leads.md` のアジェンダの項目名と題を通して読み、点検表で確かめる
8. **アジェンダは、話す順の項目名だけにする。** 主張や数字は書かない（それは要約の役目で、アジェンダとは別のページ。要約を置くかどうかは資料ごとに決める）。項目は 3〜7 個が目安で、10 個を超えない。項目名の言葉は、7 の「言葉の選び方」に従う。言い回しをそろえる。項目名と各ページのタイトルを同じ言葉にする。章立ては `createDeck` の `nav` に1回だけ書き、アジェンダのページ（`agendaPage`）・各ページのタイトル（`base` のタイトルを省くと章の項目名になる）を、そこから作る。右上の現在地（ミニ目次）は、既定では出さない（`createDeck` の `miniNav: true` で出す。タイトルが章の項目名なので、現在地はタイトルで分かる）。章の変わり目でアジェンダをもう一度出すなら、`agendaPage({ active: 章の番号 })` で今の章だけ濃くする。**8 枚以上の資料は、表紙（と要約）の後にアジェンダを必ず置く**（置かないと書き出しのときに警告。2026-11-25）。「15 枚」のような枚数の指定は、表紙とアジェンダを数えない本編の数として扱い、アジェンダを省く理由にしない
9. **主体や箱をつなぐ線は、水平・垂直と鉤線（直角に折れる線）だけにする。斜め線は使わない。** ビジネスモデル図、構成図、スイムレーン、自作の図の矢印に当てはまる。斜めの線は、交わる所や名前の置き場所が読みにくく、図が雑に見える。`bizModel` は、同じ行・同じ列に無い主体を、直角に1回折った線でつなぐ（斜めになる指定はエラーで止まる）。自作の図でも、箱と箱は鉤線でつなぐ。例外は、多くの要素が1つへ集まる・1つから分かれる線を、なめらかな曲線で束ねるときだけ（解決策の俯瞰の図）。メッセージボックスの引き出し線も、水平か垂直にする
10. **1ページで、2つの問いに答えない。** 「誰のためか」「何に困っているか」「いま、どうなっているか」「なぜ、そうなるか」は、それぞれ別のページにする。リードの2文の主語や話題が変わっていたら、2ページに分ける（2文目を足すのは、決まり11の「だから何」のときだけ）。課題を説明する順は、対象者（ターゲット）→ 悩み（一言で言うと何に困っているか）→ 現状の詳細（いまの進め方の図と、その中の課題を1つずつ）。対象者と悩みは、それぞれ1つの図で1ページ。現状の詳細は、同じ図を敷いた続きのページ（`series`）にする
11. **リードは、そのページの結論を言い切る（2026-11-27 に改めた。11-28 に文末を体言止めに）。** タイトルは話題、リードは結論を受け持つ。
    - **聴講者が疑問を持たない（合格の条件）：** 書いたら聴講者になって「何を？ どれ？ どうする？ どれくらい？」と問う。答えがリードにも同じページの図にも無ければ、書き直す。問いと答えの場所は、全ページで base の `ask` に書く（`ask: "どの工程？ → リードの「購買部の確認」／ほかの工程は何日？ → 図の時間の行"`）。`.leads.md` の「聴講者が持ちうる疑問」の欄に出る（画面には出さない）。全ページ書いてから点検する
    - **比喩・抽象語を使わない：** 足場、鍵（カギ）、土台、武器、勝ち筋、突破口、追い風、伸びしろ などは、何を・どうするで書く（「足場が要る」→「個食への参入が必要」）。この一覧は例で、一覧に無い比喩は、上の問いで見つける
    - **否定で結ばない：** 「〜ではない」「〜とは言えない」で終えず、何が言えるかを肯定で書く（「高すぎる値段ではない」→「450円の価格受容性は検証済み」）
    - **聴講者が知っている経営の言葉は使う：** 経営会議なら「価格受容性」「参入」「シェア」など。日常語の言い換えより短く正確なら、そちらを使う。題・アジェンダの項目名・図の中の名前も同じ（7）。社内の略語や呼び名は、決まり14のまま
    - **長さ：** 全体で2行・70字まで。70字は上限で、目標ではない。短く言えるなら、短いほうがよい。超えるなら、言うことを減らすか、ページを分ける
    - **結び方：** 「。」で終える。文末は名詞で止める（体言止め）。「だ」「である」は使わない。「〜する」の動詞は「する」を落とす（参入する → 参入、提案する → 提案）。それ以外の動詞は、名詞か「〜は○○」の形に言い換える（届ける → 提供、絞る → 「狙う客は〜の世帯」、取れる → 確保が可能、受け入れられる → 受容範囲内、裏づけられた → 検証済み）。名詞で止めると不自然になる文（依頼の文など）だけ、動詞のまま残してよい。体言止めでも、主張の無い見出しのような名詞の並び（「2025年度の売上推移。」）にはせず、結論を書く
    - **言い切る：** 予告（「〜について説明します」「〜を紹介します」「見ていきます」）と、ぼかし（「と思われる」「かもしれない」「可能性がある」「と考えられる」「ではないか」）を書かない。「大幅に」「多くの」「一定の」「さまざまな」は、数字にする
    - **図の根拠と合わせる：** 具体的な数字を書き、その数字は同じページの図で確かめられるようにする（同じ値を、同じ書き方で）。名指しする数値の少なくとも1つは、図の中で主役の大きさ（24pt 以上。部品の `focusValue` は 36pt、段階の道は `kpis` の `{ key: true }`）にする。小さな札に埋もれさせない
    - **だから何：** 1文目が事実だけ（数字の報告）で終わるときだけ、そのページの判断か次の行動を1つ足す。1文目がすでに判断や行動（「〜へ参入」「狙う客は〜」「〜を決めてほしい」）なら、2文目を足さない。足すのは判断1つだけで、新しい情報（理由の言い足し、利点、補足の数字）は足さない。判断は、この資料で決めること（主題・結論）にとって何を意味するかを言う。構成の「示唆」は材料にするが、作り手のメモ（比喩や話し言葉を含む）なので、言い回しは写さず、全部も書き写さない。判断につなぐ短い一言（下の「主力だけでは売上が減るため」）は、1文目とそのページの図から言えることに限る
      - 主題にとっての意味を書く例：「主力の大袋は4年で−4%、個食は+61%。主力だけでは売上が減るため、個食への参入が必要。」／「450円が入る400〜500円の価格帯は、前年比+24%と最大の伸び。450円の価格受容性は検証済み。」
      - **2文目は、資料の主題への判断で、その根拠が同じページにあること。** 事実の言い直しや、根拠がページに無い主張にしない
      - 悪い例（事実の言い直しで、判断になっていない）：「400〜500円の価格帯は、前年比+24%と最大の伸び。450円はこの帯の価格。」
      - 悪い例（根拠がページに無い）：「個食は年平均+12.7%で伸び、2026年も3,260億円へ増加。参入は今。」（なぜ今なのかを示すものが、ページに無い）
      - 足す例：「よく買うのは共働きの世帯で、52%が月1回以上購入。」→「共働きの世帯は、52%が月1回以上購入。狙う客は30〜40代の共働きの世帯。」
      - 足さない例：「首都圏100店で3か月売り、2つの基準を満たせば本格参入。」→「首都圏100店で3か月売り、月6万食・リピート率30%を超えたら本格参入。」（1文目が行動なので、これで終わり。「大きな投資の前に、売れ行きだけを検証。」を足すのは蛇足）
    - **削る：** タイトルで分かることを言い直さない（タイトルが「ターゲット」なら、「対象は」と書き出さず中身から書く）。熟語で縮める（自分のお金で → 自費で、確かめる → 検証する、もう一度 → 再度、たくさん → 多数、配る → 配布する、広げる → 展開する、〜することができる → 〜できる。ただし、図の中の名前と同じ言葉は変えない）。接続の言葉（そこで、だから、また、なお）と、意味を足さない語（〜という、〜のような、〜していく）を削る
    - **確かめ方：** `deck-parts.js` は、長さ、「。」の終わりと「だ」「である」の結び、動詞で終わる文、予告とぼかし、否定の結び、比喩・抽象語の例、数字にする言葉、図に無い数字、図の中で大きくない数値、疑問の欄が空のページ、タイトルで分かる書き出し、縮められる言い回し（`createDeck` の `wordy` で足せる）を警告する。聴講者の疑問に答えているか、「だから何」、蛇足は機械では分からないので、書き出される `<資料名>.leads.md`（ページ・タイトル・リード・疑問の一覧）を通して読み、点検表で確かめる
12. **図の中の文・メッセージボックス・表の文も、リードと同じ基準で縮める。** 図の中の名前、箱の説明、表のセル、メッセージボックスの見出しと本文に、11 の「削る」（熟語で縮める、意味を足さない語を削る）を当てる（確かめる → 検証する、お金をとらない → 無料、一緒に試す → 共同で試行、使う人 → 利用者）。名前の言葉は 7 の「言葉の選び方」に従う（短くするために造語を作らない）。メッセージボックスは、見出し全角20字まで、本文の1文は全角36字まで。同じ物は、資料の中で同じ言葉で呼ぶ（リードで「利用者」と書いたら、図の中も「利用者」）。体言止めや名詞の並び（「資料の要否、出席者、共有先」）で短くしてよい。`deck-parts.js` は、描く文字のすべてを同じ一覧で見て、縮められる言い回しを警告する。警告が出ない所も、声に出して読み、削っても意味が変わらない語を削る
13. **色は、題材に合わせて資料ごとに決める。指定がなければ、内容に応じて選ぶ。** 元になる素材（動画、サイト、ブランド）があれば、その色にそろえる。無ければ、題材の分野と読み手から、強調の色を1つ選ぶ（`createDeck` の `theme`。名前で選ぶ: `blue`＝IT・スタートアップ、`teal`＝医療・公共、`green`＝環境・食品、`orange`＝小売・教育、`purple`＝クリエイティブ・AI、`slate`＝金融・製造、`navy`＝落ち着いた報告書。または `{ emph: "色" }`）。選んだ色と理由を、build.js の先頭に書く。決めないと警告が出る。プロジェクトか個人の theme.json に色（`colors`）があるときは、選ばずにそれを使う（build.js に `theme` の色を書かない。下の「テーマ」）。文字の色（`ink`）と強調の色（`emph`）は分けて持つ。色を替えても、役割は変えない（強調は1ページ1か所、問題は `accent` の赤、退かせるものは灰）。赤は問題の色なので、強調の色に選ばない。色は強調の1色と灰だけで組み、色数を増やして飾らない。線の絵（1色のアイコン）は、資料の色の組に合わせて塗り直す（`scripts/tint_icons.py`。決まり15） ただし、テーマのファイル（theme.json）に会社の色があれば、それを使う（題材で選んだ色より優先）。
14. **略語や区分の名前には、それが何を指すかを一言で添える。** TAM・SAM・SOM、KPI の略語、段階の名前（フェーズ1）、社内の呼び名は、名前と数値だけでは読み手に伝わらない。名前の横に、何を指すかを全角12字までで書く（TAM　高所得国のホワイトカラー）。`tamSamSom` は `items` の `what` に書く（円の中に出る。無いと警告）。ほかの図でも、略語だけの見出し・ラベルを作らない
15. **絵（アイコン）は、有効な所に置く。** 有効なのは、(1) 種類の違うものを見分けさせるとき（主体、段階、費目、リスクと対処）、(2) 値が何の値かを一目で示すとき（条件の行、指標）、(3) 外部の製品・会社（5）。置かないのは、文の飾り、同じ絵の繰り返し、絵にしても意味の取れない抽象語（「価値」「戦略」）。絵だけにせず、名前か値を必ず横に添える。1つの資料の絵は、同じ線の太さ・同じ作りにそろえる（元になる素材に絵があれば、その形を使う）。色は意味で決める：文字の色＝ふつう、強調の色＝強調・対処、赤＝問題、白＝色を塗った丸の上。絵を足して文字が枠からはみ出すなら、文字を縮める。**絵は、1つの組からそろえて使う。** 線の絵は `icons/` の1組（一覧は `icons/CATALOG.md` と `icons/_catalog.png`。65個）から選ぶ。色は、色の組を決めたあとに `python3 <skills>/pptx-deck-design/scripts/tint_icons.py icons --ink <文字の色> --emph <強調の色>` で塗り直す（文字の色・白 `-w`・強調の色 `-e`・問題の色 `-r` の4色ができる。部品では `d.icon(s, 名前, cx, cy, 大きさ, "w"|"e"|"r")`）。塗っていないと警告が出る。無い絵は、同じ作り（48×48 の枠、線の太さ 3.4、角は丸）の SVG から `pic-<名前>.png` で足し、もう一度塗る。外部の製品・会社の公式のアイコンは塗らない
16. **重要な数値は、色や枠だけでなく、大きさで示す。** 主役の数値（リードが言う数値、表の決め手の値、主役の棒の値）は、周りの値の1.5〜2倍の大きさにする（本文 19pt に対して、グラフの見る所の値は 36pt）。色や枠で囲むだけでは、3秒で目に入らない。大きくするのは1ページに1つ。大きくするのは数値と短い語（全角12字まで）で、長い文は大きくしない（太字と塗りにとどめる）。`colBars` の主役の値は 36pt、`compareTable` の決め手のセル（`focus`）は数値 22pt、`tamSamSom` の狙う金額は 36pt。「図の中の文字サイズは4段まで」は、この主役の1つを含めて数える
17. **表は、線と余白で組む。行に背景色を敷かない。** 行の全幅に背景色を敷いた表（帯の表・縞模様）は、情報が読みにくいので使わない（縞模様は、行の少ない表では強調に見える）。表の作法：(1) 見出しを本文と分ける（太字と、下の線1本）、(2) 行の間は薄い細線（0.5pt）と余白、(3) 縦線・外枠・格子は使わない、(4) 数値は右揃え・文字は左揃え。見出しも列の中身と同じ側にそろえる（行ごとに単位の違う評価表は左揃え）、(5) 単位は見出しか行見出しに1回だけ、桁数をそろえる、(6) まとまりは余白と小さな見出しで分ける、(7) 目立たせるのは決め手の値1つ（大きさ・太字・そのセルだけの塗り）、(8) 行が多い・数値の推移を読ませたい表は、グラフにする。表の強調で背景色を使ってよいのは、決め手のセル1つ、推奨の1列の枠、選ぶ1行だけ
18. **表は小さく、大きな文字で、違いが形に出るように組む。表にする前に、表でなければならないかを疑う。** 表が読みにくくなる原因は3つある。(1) 小さく薄い文字の短い語が、スライドの幅いっぱいに散っている、(2) どのセルも同じ重さで、どこが違うのかを読み手が探すことになる、(3) 1つの主張を伝えたいのに、値を引くための形（表）を使っている。直し方：
    - **主張に効く行だけ残す。** 5行×4列まで（超えると警告）。目安は3行×3列。効かない行は、付録か台帳へ移す
    - **行を詰める。** 行の高さは、文字の高さの約2倍。本文の領域に合わせて引き伸ばさない。間が広いと、行にも列にも見えず、語が散って見える。余った場所は空けておくか、表の横に結論を置く（`note`）
    - **値を主役にする。** 値は濃い 20pt。行の名前と列の見出しは、控えめな 19pt（soft の色。行の名前は太字にしない）。枠組みの文字が値より目立つと、値が後回しになる
    - **1つの表には、同じ種類の値だけ。** 数値・語・評価の丸を混ぜない（列を縦に読めなくなる。混ざると警告）。「判断」の行も、種類の違う行なので置かない。結論は、リードか表の横に書く
    - **文字は小さくしない。** 入らないなら、行を減らす
    - **表の幅は中身に合わせる。** スライドの幅いっぱいに広げない（`compareTable` は、列の幅を中身に合わせて狭める）
    - **セルに文字を入れない。** 数値・ゲージ・評価の丸・星だけ（決まり20）
    - **違う値だけ濃く。** 行の中で、ほかの列と同じ値は薄くなる（自動）。決め手の値1つは、大きく
    - **言いたいのが「違い」なら、表をやめる。** 前と後を並べた図、棒、決め手の数値を大きく置く形のほうが、3秒で伝わる。表は、読み手が値を引く・見比べることが目的のページにだけ使う
    - **表は最後の手段。** 先に、図・棒・大きな数値で伝えられないかを考える。表を使うのは、読み手が値を引く・見比べることが目的のページ（付録、仕様の一覧）だけ。PowerPoint の表の機能（`addTable`）は、どの場合も使わない（罫線と塗りの既定の書式が入り、位置と余白を細かく決められないため。表は、文字と線の図形で組む）
19. **単位や桁の違う数値を、表の縦横に並べない。** 「2」「840」「24」のように桁の違う数値が並ぶと、比べる相手でない数字どうしを見比べてしまう。数値を比べるときは、(1) 比べるのは同じ指標の中だけ。指標ごとに尺度をそろえた棒にする（`metricBars`。行＝比べる対象、列＝指標）、(2) 数字の並びではなく、長さで見せる。値は棒の先に添える、(3) 単位は指標の見出しに1回だけ、(4) 主役の対象の棒だけ強調の色、決め手の値1つを大きく。`compareTable` は、行ごとに数値の桁が10倍以上違うと警告する
20. **表のセルに、文字を入れない。** 表は、一目で比べるためのもの。全部読まないと分からない表は、表の意味をなさない。セルに入れてよいのは、数値、ゲージ（`{ bar, max }`）、評価の丸（`{ ball: 0〜4 }`）、星（`{ stars: n }`）と、全角4字までの短い札（「なし」「Mac」）だけ。評価の丸に根拠の文を添えない。文字のマトリクス（`blockTable`）は使わない。文字で説明が要る内容は、表にせず、箇条書き（`points`）か図にする。比べたい中身が文でしか書けないときは、情報の設計に戻る：比べる軸を、満たす・満たさない、多い・少ない、で答えられる形に言い直す（「覚え方」→「普段の作業から覚えるか」）。`compareTable` はセルの文字を、`blockTable` は呼ばれたことを警告する
21. **表以外の図でも、マス目に文を積まない。** 工程の流れ、段階の計画、決裁の一覧を、行と列のマス目に文で埋めると、表と同じく、全部読まないと分からない。(1) 工程の流れ（`processFlow`）は、工程の名前・所要・短い札（全角12字まで・1行）だけ。行は2行まで。工程ごとの説明は、同じ図を敷いた続きのページのメッセージボックスで言う。(2) 段階の計画は、段階×観点の表（`journeyMap`）を使わない。段階の道（`roadmap`）が候補で、段階ごとに置くのは、名前・時期・絵・次へ進む条件の値（4つまで）だけ。ただし、持ち帰るのが進むか決める1〜2個の値なら、その値がいちばん大きく見える形にする（同じ大きさの札の中に埋めない）。(3) 決裁の一覧（`decisionPage`）は、決めてほしいことを1ページに1つにして、選択肢を図か数値で見せる。どれも、超えると警告が出る。図の中の文字は、名前・値・短い札にとどめ、文はリードとメッセージボックスに書く
22. **補足の小さく薄い文字を足さない。** 名前の下に小さく灰で添える補足（`sub`、主体やノードの説明、列見出しの2行目、棒の下の説明行）は、書くか消すかを決めずに逃げた跡で、読まれず、見る所を散らす。要る中身は、名前そのものに書く（単位は「売上（億円）」のように名前の後ろ、製品名は見出しに2行で）。要らないなら消す。何の数値か・出典・時期・凡例のように読み方に要る情報は、本文の大きさの読める色（soft）で書く（部品の側でそうしてある）。灰を使ってよいのは、軸の目盛り・フッター・退かせるデータの値のような短い語だけで、説明には使わない。同じ言葉を2か所に置かない（円の中と行の両方に書く、など）。`deck-parts.js` は `sub` を使うと警告し、灰の小さな文を描くと警告する。色にかかわらず、図の中に小さすぎる文字を描いても警告する。図の中の文字は、ラベル・軸・注記も含めて 18pt 以上（例外は、密な図＝スイムレーンとガントの 16pt と、付箋のボード）、色は本文の色（soft 以上）。灰・薄い色（gray・pale・faint）は線と図形にだけ使い、文字には使わない（部品が自動で soft に描き直す。例外はフッター）。入らないときは、文字を縮めず、言葉を短くするか図を広げる。例外は付箋のボード（`stickyBoard`。ブレストの洗い出しで、量を優先して 6pt 前後）
23. **グラフは、見る所が一目で分かるようにする。** 1つのグラフの区分は、1つの切り口にする（世帯の区分と年代のように別の切り口は、別のページか、同じ図の続きのページ。`hBars` の空行で区切るのは、全体と内訳のように切り口が同じときだけで、`oneCut` にその切り口を書く）。凡例の箱は置かず、系列の名前は図の中に直接書く。1つのグラフで強調の色を付けるのは、見る所だけ（棒・点・線・帯）。他はすべて灰にする。比べる2系列でも、系列ごとに色分けして全体を塗らない（比べる相手は濃い灰、残りは薄い灰）。見る所の値は 36pt・太字・強調の色（問題なら赤）で、見る所のすぐ隣に書く（`focusValue`、`FOCUS_FS`）。見る所の線は 3pt、他の線は 1.25pt。リードは見る所の名前か値を名指しする。計画のガントも、リードが言う作業の帯だけ強調の色にし、他は灰（`task.focus`）。グラフのページで、見る所の大きな値（24pt 以上で、強調の色・赤・塗りの上の白の文字）が無い／2つ以上なら、部品が警告する 見る所の値は、その要素の普通の値の位置に書く（棒なら棒の上、区画なら区画の中に白で、点なら点の隣）。離れた所や図の外に置かない。数値のカードを並べる形（KPI タイル）と、同じ指標を区分ごとに小さく並べる形（スモールマルチプル）は使わない。グラフは読みやすい密度で描き、余白は残してよい。棒の太さと間・名前の位置は部品が決める（`references/charts.md` の「棒の作法」）。
24. **聞き手の前提を最初に決める（2026-11-25）。** 聞き手が、その事業・製品・考えを初めて聞くのか（`first-time`：社外、投資家、新しい提案を初めて聞く役員）、前提を共有済みの内部の人か（`insider`）を、build.js の `createDeck` の `audience` に書く（書かないと警告）。依頼や構成から読み取り、分からなければ初見として作る。**初見なら、新しい物は「一言で何か」を中央に大きく出すページ（`concept`）から入り、仕組み（`bizModel`・`processFlow`・`archDiagram`）や他社と比べる図は、その次のページから見せる**（先に仕組みの図を出すと警告）。理解の無い人に、いきなり仕組みや比較を見せても分からない。コンセプトのページには、一言（全角30字まで）と要点3つまでだけを置き、仕組みや比べる話を入れない。一言で言えないなら、何が新しいのかを決め直す。内部の人には、前提の説明を省き、論点や数字から入ってよい
25. **形を選ぶ前に、そのページで読み手が持ち帰る1つ（語か数値）と、それを支える情報を決める。形と強調は、そこから逆算する（2026-11-25、2026-11-27 に改めた）。** build.js の各ページの前に、`// 伝えたいこと：…／持ち帰る1つ：…／支える情報：…` を書く。形は、持ち帰る1つがいちばん大きく見えるものを選ぶ。手元の中身の形（列挙・段階・比較の表）から部品を決めない（原稿が「中身」を箇条で書いていても、言いたいことが1つなら、その1つを大きく見せる）。**部品は使うが、無理に使わない。** 持ち帰る1つを大きく見せられる部品が無ければ、基本の図形（文字・四角・線。`T`・`rect`・`hline`）で描いてよい。新しい図の形を考案するのではなく、持ち帰る1つを大きく置き、支える情報をその隣に置く。1ページ1メッセージ、見る所1つ、読める大きさは守る。データのページは数字の比べ方から形が決まりやすいが、コンセプトや考え方のページは、属性を並べて終わりやすい。コンセプトのページは、価値（何が、何と比べて、どれだけ違うか）を一目で見せる。属性（誰に・何を・いくらで）の箱を並べない。価値の差が1つの物差し（時間・量・回数・価格など）で言えるなら、`concept` の `contrast` で、比べる相手と自社を同じ物差しに並べ、自社の行だけ強調する。物差しで言えないなら、一文だけを中央に置く（`concept` を `contrast` なしで）。**コンセプトのページは一点突破にする。** 伝える価値は1つ、物差しは1本、比べる相手は1つ（自社と2行）。マジックワード（短い言い切り。例「畑から冷凍まで、当日。」）で言えば、それで事足りるようにする。2つ目の価値（その結果の鮮度の値など）や、比べる相手を足さない（足すと、何が突き抜けているかが薄まる）。説明の小さな文（名前の札・物差しの説明・帯の端の札）も置かない。目盛りと行の名前と大きな一語で読めるようにする（2026-11-25）。**`concept` の帯の対比（`contrast`）は、一例にすぎない。** 価値を一目で見せる形は、題材でまったく変わる。逆算して、その価値がいちばん伝わる形を毎回選ぶ（例：時間・量・回数の差なら同じ物差しの帯、時間とともに開いていく差なら線、手間や工程が減るならアイソメトリックの図解や流れ、場所や規模なら俯瞰の図、見た目そのものが価値なら写真や画面）。部品に無い形は、決まり6のとおり、ページに合わせて描いてよい（そのときも、伝える価値は1つ・見る所は1か所・説明の小さな文を置かない）

## 決まりがぶつかったときの決め方（2026-11-24 に洗い出した）

上にあるものを優先する。

1. **依頼者がその資料について言ったこと**（札を外す、色を指定する、など）
2. **1ページ1メッセージと、見る所を1つにすること**
3. **読めること**（図の中の文字は 18pt 以上・本文の色、枠からはみ出さない、フッターの線に掛けない）
4. **形・色・絵・言い回しの決まり**
5. **密度や空きの目安**

個別の決め方：

| ぶつかる決まり | 決め方 |
|---|---|
| 前面の箱は「どのページでも同じ位置」と「隣のセルをちょうど覆う」 | 見る所を隠さないことが先。次に、薄くした文字に半端に重ねない（空きに置くか、ちょうど覆う）。同じ位置にするのは、それができるときだけ |
| `journeyMap` の文字 8.5pt と「図の中の文字は 18pt 以上」 | `journeyMap` は使わない（21）。`roadmap` で描く |
| 密度を高く、と、マス目に文を積まない（21） | 21 を優先する。空きは空けておく。密度は、値と絵で作る |
| 外部の製品は名前があればアイコン必須（5）と、同じ絵を繰り返さない（15） | 同じ製品が1つの図に何度も出るときは、最初の1か所（見出しや主体）にだけアイコンを置く。警告は、そのページに1つあれば出ない。アイコンを置くと見る所より目立つなら、その行ごと削る |
| 枚数の指定（「15 枚」など）と、アジェンダを必ず置く（8） | アジェンダを置く。枚数の指定は、表紙とアジェンダを数えない本編の数として扱う（2026-11-25） |
| 「サマリー・まとめのページは置かない」と「要約は資料ごとに決める」（8） | 話して見せる資料には置かない。送って読ませる報告書は、冒頭に要約を1枚置いてよい（アジェンダとは別のページ）。末尾のまとめは、どちらでも置かない。構成に要約のページがあれば置き、`summary` で描く（決めてほしいことを上に1つ、根拠を下に2〜4個、線でつなぐ。`points` の羅列にしない。2026-11-25） |

| 題は構成（原稿）の項目名と、普通に使う言葉（7） | 普通に使う言葉に言い換える（意味は変えない。言い換えた所は返答で知らせる）。依頼者がその言葉を指定したときは、そのまま |
| 題は項目名（7）と、送って読ませる報告書 | 報告書でも題は項目名。結論はリードに書く。題に結論の1文を書く形（アクションタイトル）は使わない（例外を作らない） |
| 仮値に（仮）を付ける、と、札を出さない | 実在の資料の、確かめていない値には（仮）を付ける。架空の題材・見本の値、例として置いた社内の決まりの値には付けない。依頼者が札を外すと決めた資料では付けず、台帳に残して、返答で伝える |
| 推奨の列を枠で囲む、と、列や行の丸ごとは見る所にならない（3） | 列の枠は、どの案を選ぶかが主張の評価表だけ。それ以外は、決め手のセル1つ |
| 表に罫線は使わない（以前の決まり）と、表の定番の作法（17） | 17 を優先する。見出しの下の線1本と、行の間の薄い細線は使う。格子・縦線・外枠は使わない |
| 情報密度は高くする、と、補足の文字を足さない・短く言い切る（11・12） | 密度は、数値・条件・根拠で作る。補足の文や飾りで作らない |
| 密度の目安「評価表は 5〜7軸＋判断 × 3〜4案」と、表は小さく（18） | 18 を優先する。5行×4列まで・値は 20pt。軸が多いなら、主張に効く軸だけ残す |
| 文字サイズは4段まで、と、重要な数値は大きく（16） | 大きくした主役の1つを含めて4段に収める |
| 汎用的な図解を使う、と、俯瞰の図は自作してよい（6） | 比べる・推移・内訳は定番の図。全体の仕組みの俯瞰と、元の素材に同じ図があるページは、その形で描く |
| 仮値で埋めて形式を下げない（`argument-and-evidence.md`）と、原稿に無い値を長さ・位置・角度にしない | 原稿に無い値を図にしてよいのは、台帳に出どころか仮の前提があり、図に値と（仮）の札を書くときだけ。値を書かずに長さや位置だけを置かない。範囲しか分からない値は、仮値でつぶして棒にしない |
| 構成案に無い要素は足さない、と、アイコンを有効な所に置く（15） | アイコンと、論旨を支える数値は、足してよい。足さないのは、分類ラベル・補足・別の論点 |
| 表紙は題と日付だけ、と、ピッチの一言の副題 | ピッチ・会社紹介は、何の事業かを一言で言う副題を足してよい |
| 見本（`sample-*.js`）の書き方と、今の決まり | 見本は今の決まり（1〜23）に合わせてあり、部品の警告は0件。食い違ったら決まりを優先する |
| 計画のガントは「見た目を1種類にそろえる」と、グラフの見る所（23） | 帯の太さ・形は1種類のまま。色だけ、リードが言う作業の帯を強調の色にし、他は灰にする |

## 始め方

以下の `<skills>` は、スキルの置き場所。プラグイン（pptx-deck-kit）として入れたときは `${CLAUDE_PLUGIN_ROOT}/skills`。スキルの folder を直接置いたときは `~/.claude/skills`（Codex は `~/.codex/skills`）。

0. **チームの決まりを最初に読む。** 個人の `~/.claude/pptx-deck/rules.md` と、プロジェクトの `.claude/pptx-deck/rules.md`（作業フォルダから上へ探す）があれば、このスキルの他のファイルより先に読み、このスキルの決まりより優先する。両方あれば、プロジェクトが個人より優先する。ただし**芯の決まりは外せない**：1ページ1メッセージ、見る所は1か所、マス目（表・塗りブロック）に文を積まない、テーマで下げられる文字の下限（題 20pt、リード 18pt、やや大きい文字・名前・本文・注 14pt、主役の値 24pt）。rules.md がこれらを外すよう書いていても芯の決まりに従い、そのことを返答で伝える。rules.md で外した（このスキルと違う）決まりは、点検（手順の7）の報告に「rules.md により〇〇を外している」と書く。見た目（色・書体・フッターなど）は rules.md でなく theme.json に書く（下の「テーマ」）
1. 作業フォルダは、資料と一緒に残す場所にする（例: プロジェクトの `decks/<資料名>/`。build.js・pptx・画像をここにまとめる）。Claude の一時フォルダ（scratchpad）には置かない（後で直せなくなる）。作業フォルダに、`<skills>/pptx-deck-design/assets/deck-parts.js`・線の絵のフォルダ `<skills>/pptx-deck-design/assets/icons/`（`icons/` ごと）・既成のテーマのフォルダ `<skills>/pptx-deck-design/assets/themes/`（`themes/` ごと）・始めに近い見本（`sample-charts.js`・`sample-flow.js` など。題材の形に近いもの）をコピーする。`deck-parts.js` はスキルの置き場所から `require` しない（後でライブラリを直したとき、過去の資料の再生成結果が変わるのを避ける）。アイコンは、コピー先・作業フォルダの順に探す
2. 見本を `build.js` に名前を変え、ページを書き換える。新しい資料は、この見本から始める
3. pptxgenjs：プラグインとして入れたときは、入れたときに自動で入っている（`${CLAUDE_PLUGIN_ROOT}/node_modules`）。スキルを直接置いたときは、作業フォルダで `npm install pptxgenjs@4.0.1 jszip@3.10.2` する
4. 色の組（`theme`）を決めたら（theme.json の色を使うときも）、作業フォルダの線の絵を塗り直す: `python3 <skills>/pptx-deck-design/scripts/tint_icons.py icons --ink <文字の色> --emph <強調の色>`（色は、塗っていないときに出る警告に書いてある。Pillow が要る）
5. 実行: プラグインのときは `NODE_PATH="${CLAUDE_PLUGIN_ROOT}/node_modules" node build.js <出力先.pptx>`。作業フォルダに npm install したときは `node build.js <出力先.pptx>`
6. 画像にする（手順の6）には、PowerPoint（Mac）か LibreOffice と、pdftoppm（poppler）か PyMuPDF・Pillow（`pip install pymupdf pillow`）が要る

## テーマ（トンマナとフォーマット）

会社や個人の見た目（色・書体・文字の段・背景・飾り・ヘッダー・章ナビ・フッター・表紙・文字の置き場所・自分のアイコン）は、JSON の「テーマ」に書いて差し替える。プラグインは更新のたびに丸ごと入れ替わるので、各自のテーマはプラグインの外に置く。

**置き場所と優先の順**（上ほど優先。項目ごとに上が勝ち、書いていない項目は下から引き継ぐ）:

1. build.js の `createDeck(pres, opts)` の opts（`footer`・`footerText`・`copyright`・`logo`・`font`・`sizes`・`layout`・`cover`・`pageNumber`・`confidential`・`iconDir`）
2. `opts.theme`：色の組の名前（`blue` など）、既成のテーマの名前（`standard`・`corporate`・`pitch`）、テーマの JSON のパス、オブジェクトのどれか。今の書き方（`"blue"`、`{ emph: "2F6BFF" }`）もそのまま使える
3. プロジェクトの `.claude/pptx-deck/theme.json`（作業フォルダから上へ探す）
4. 個人の `~/.claude/pptx-deck/theme.json`
5. 部品の既定（何も置かなければ、今とまったく同じ出力）

- **会社の色が優先。** 個人かプロジェクトの theme.json に色（`colors`）があれば、build.js の `theme` に書いた色は使わず、会社の色で描く（「会社の色を使い、build.js の theme の色は使わなかった」と1行出る）。会社の色が無いときだけ、題材に合わせて色を選ぶ（決まり13）
- 再生成の結果が、個人の theme.json の書き換えで黙って変わらないよう、資料を仕上げたら、使ったテーマを作業フォルダに写して `opts.theme` にパスで渡す。テーマのファイルを読ませないときは `createDeck(pres, { themeFiles: false })`（または環境変数 `PPTX_DECK_THEME_FILES=0`）
- 形の例（項目の一覧は `references/tokens.md` の「テーマの設定の項目」）:

```json
{
  "extends": "corporate",
  "colors": { "emph": "00806E" },
  "font": { "face": "BIZ UDPGothic", "heading": "Meiryo" },
  "sizes": { "body": 19, "lead": 22, "focus": 36 },
  "footer": { "style": "band", "copyright": "© Example Inc.", "confidential": "社外秘", "logo": "logo.png" },
  "cover": { "style": "full", "affil": "株式会社エグザンプル 経営企画部", "logo": "logo.png", "logoPos": "top-left" },
  "layout": { "titleY": 0.46, "leadY": 1.12 },
  "icons": "my-icons"
}
```

パス（ロゴ・アイコンのフォルダ・`extends` のパス）は、その JSON の場所から読む。

**替えられる所**：色のトークン、本文・見出し・数字の書体、文字の段（題・リード・やや大きい文字・名前・本文・注・主役の値）、フッター（帯かページ番号だけか、ページ番号の有無、資料名、著作権の表記、ロゴ、「社外秘」などの表記、帯の色）、表紙の型（今の2つの型から選ぶ）・所属・ロゴ、題・リードの位置、背景と飾り（ページの種類ごと。`master`）、章ナビ（`nav`）、帯の高さ、本文の下端と左右の余白（決まった範囲）、自分のアイコンのフォルダ。

**替えられない所（固定）**：スライドの大きさ（16:9。4:3 には対応しない）、本文の上端（y 2.2）、本文のページの地は薄い色（濃い地の本文には対応しない）、部品の中の固定の大きさ、色の役割（強調は1か所、問題は赤、退かせるものは灰）。テーマで本文の下端が上がる・余白が広がると図は小さくなるので、警告が出たら項目を減らすかページを分ける。文字の段は、テーマで下げられる下限（題 20pt、リード 18pt、やや大きい文字・名前・本文・注 14pt、主役の値 24pt）を下回る値を使わず、下限にして警告する。この下限は、図の中の文字を 18pt 以上にするという決まり（22）とは別のもの。

**既成のテーマ**（`assets/themes/`。`opts.theme` か theme.json の `extends` に名前で書く）:

| 名前 | 見た目 |
|---|---|
| `standard` | 今の既定と同じ（紺の1色、BIZ UDPゴシック、ページ番号だけのフッター、題と日付の表紙）。全項目を書いてあるので、自分のテーマの写しの元にもなる |
| `corporate` | 紺の会社資料。題・表紙・章扉はメイリオ、下に紺の帯のフッター、表紙は題の下に短い線と日付・所属 |
| `pitch` | ピッチ。強調の色が鮮やかな青紫、題は 28pt、フッターはページ番号だけ |

**会社の pptx から作る**：`python3 <skills>/pptx-deck-design/scripts/theme_from_pptx.py <会社の pptx・potx・thmx> <出力の theme.json> [--logo-out <フォルダ>]`。テーマの色（dk1・lt1・accent1〜6 など）と書体（見出し・本文の latin・日本語）、表紙・章扉・本文のレイアウトの背景（画像にする）と文字の置き場所、章ナビ、ページ番号の形を読んで書き出す（元のファイルは書き換えない）。背景の読み取りには PowerPoint か LibreOffice、Pillow が要る。使うレイアウトは `--cover`・`--chapter`・`--content <名前>` で選べる。デザインがレイアウトでなくスライドに直接描かれた pptx は、`--cover-slide`・`--chapter-slide`・`--content-slide <番号>` でスライドから読む（文字・表・グラフは外し、本文は端の飾りだけ使う）。`.thmx` からは背景を読まない。背景に残したくない固定の文字は `--drop-text`、色と書体だけでよければ `--no-design`。`--no-design` のときや背景が読めないときは、ロゴらしい画像とフッターの文字を読む。**出した後は、見本の3ページを画像にして、元のテンプレートと見比べる**（題が絵に重なる、本文の背景を使わなかった、などは出力の行と警告に出る）。読み取れなかった項目は書かない（既定に任せる）。どの色を強調（`emph`）に当てたかを表示するので、違えば `colors.emph` を直す。ロゴは名前に logo を含む画像か、背景ほど大きくない画像のうち一番大きいものを取るので、飾りの画像を拾っていないか目で確かめる。出した theme.json は、プロジェクトの `.claude/pptx-deck/` か `~/.claude/pptx-deck/` に置き、ロゴの画像も同じフォルダに置く。

**書体**：既定は BIZ UDPゴシック（`BIZ UDPGothic`）。Noto Sans JP は `font.face: "Noto Sans JP"` で選ぶ（配る相手の PC に入っていると分かっているときに使う）。pptx は開く PC の書体で表示される。BIZ UDPゴシックは Windows 10・11 に入っている。入っていない PC では Google Fonts（OFL）から入れる。画像にして確かめる PC に書体が無いと、`render_pptx.sh` が知らせて代わりの書体で描くので、その画像では折り返しを判断しない。書体を替えたときは、字の幅が違うので、部品のあふれの警告と画像で確かめる（メイリオは英数字が游ゴシックより約1割広い。`font.widthScale` で見積もりを合わせる。メイリオは既定で 1.12）。
書体がこの機械にあるかは、`render_pptx.sh` の最後に出る `[render] 書体：…` の行で判断する。`ls` や `fc-list` で自分で調べて決めつけない（権限で読めないことがある）。画像の文字が□や別の書体でも、その行が「ある」なら書体はある。もう一度書き出す。画像の確認のために、build.js の書体を替えない

## 手順

1. 聞き手の前提（初見か、前提を共有済みか。決まり24）を決める。`references/argument-and-evidence.md` に従い、資料の論旨を1文で書き、各ページの「読み手の問い」「伝えたい1文」「内容の種類」（市場規模、比較、反省、経緯、原因、手順、費用、事実の列挙…）を書き出す。形式を先に決めない
2. 問いに答えるのに必要な情報を、論点の型から書き出す。手元に無い数値は追加調査し、調べても分からない値は仮値で埋める。すべて `data-ledger.md` に記録する
3. ページごとに、読み手が持ち帰る1つ（語か数値）と、支える情報を書く（決まり25）。その1つがいちばん大きく見える形を選ぶ。`references/form-selection.md` は候補の例（合う形が無ければ基本の図形で描く）。build.js の先頭に、形の割り当て（どの形を何に使うか）を書く。手元の数値で描けるかどうかで形式を決めない。「却下された形式」は使わない。図にする必要がない内容（事実の列挙、総括）は箇条書きか文章にする。build.js を書く前に、全ページの題とリードを先に並べる。題は普通に使う言葉で何のことか分かるか（決まり7）、リードだけを通して読んで話が通るか、聴講者が疑問を持たないかを確かめる（決まり11）
4. 構造が決まらないページは、pptx に入れる前にアーティファクトか画像で2〜3案を見せて選んでもらう。ユーザーに直接聞けない環境（作業リポジトリの CLAUDE.md が確認の経路を定めている場合など）では、その経路で聞き、回答までは持ち帰る1つがいちばん大きく見える案で進める
5. `deck-parts.js` の部品で描く（`references/components.md`。合う部品が無いページは、決まり25のとおり基本の図形で描く）。同じ役割のページは同じ部品で、同じ図は同じ関数・同じ引数で描く
6. 全ページを画像にする: `bash <skills>/pptx-build-sync/scripts/render_pptx.sh <pptx> <出力dir> 70`。PowerPoint で書き出せないときは、自動で LibreOffice に切り替わる。soffice（LibreOffice）を直接呼ばない（日本語の書体がつながらず、文字が□になる）
7. 画像を1ページずつ見て `references/review-checklist.md` を当て、No を直す。`deck-parts.js` の警告（console.warn）も直す。`<資料名>.leads.md` を通して読み、題の言葉、話の流れ、蛇足、聴講者の疑問への答えを確かめる。rules.md でこのスキルの決まりを外したところは、点検の報告に「外している」と書く
8. スクショで指摘を受けたら、指摘された箇所だけを直す。了承なしに要素やページを消さない
9. 構成（原稿）の言葉を言い換えたら、最後の返答で「前 → 後」を知らせる（決まり7）。仮値が1つでもあれば、最後の返答で調査を依頼する（結論に効く順に、確かめる数値・理由・当たる先・差し替える場所）

論旨を支える情報（数値、比較の対象、根拠）は、了承なしに足す。論旨そのものや論点の順序は変えない（意味を変えない言葉の言い換えは、了承なしでよい。決まり7）。変えたいとき、1ページに収まらない、同じ事実が重なる、論理が飛ぶときは、分割・統合・橋渡しページの追加を提案する（実行は了承の後）。

| 層 | 役割 | 書式 |

| タイトル | いまどの話かの項目名だけ（全角14字まで。アジェンダの項目名と同じ言葉） | 26pt bold ink |

主役の図より下（y 6.6〜）には何も置かない。例外は、1行の出典または詳細へ飛ばしたい数値のリンク（`source`）だけ。章のない資料ではミニ目次も置かない。題の上には何も置かない。

タイトル: いまどの話かの項目名だけを書く（「集客チャネルの比較」）。主張（「成果が出たのは紹介だけ」）はリードの最初の文に書き、タイトルに「：」でつながない。章立て（`nav`）がある資料では、タイトルを省けば章の項目名になる。同じ章のページが続いても、タイトルは変えない。

図の値: **原稿に無い値を、長さ・位置・角度にしない。範囲しか分からない値は棒にしない。** 棒の長さ、点の位置、円の角度にしてよいのは、原稿にある値か、調査・計算で足して `data-ledger.md` に出どころを書き、図にも値を書く値だけ。見た目の釣り合いで長さや位置を決めない（値を書かない帯でも、長さは値として読まれる）。「100g以上は120品目のうち8品だけ」から分かるのは件数で、残り112品が何gかは分からないので、gの棒にしない。件数どうしを比べる形に替えるか、文字で言う。依頼者が「構成の数字だけを使う」と言った資料では、調査の値も仮値も足さない。

数値: 論旨に必要な値は、構成案に無くても調査して書く。調べても分からない値は仮値で埋め、図の値に「（仮）」を付ける（架空の題材や見本の値、例として置いた社内の決まりの値は、仮値に当たらないので付けない。依頼者が札を外すと決めた資料では付けず、台帳に残す）。出どころを言えない値を、事実の書き方で置かない。すべての値を `data-ledger.md` に記録する。

## 既定（2026-11-08 依頼者が承認）

1. 表は、見出しと本文を線1本で分け、行の間は薄い細線（0.5pt）と余白で分ける。行の全幅に背景色を敷く表（帯の表・縞模様）は使わない（2026-11-24。情報が読みにくい）。格子・縦線・外枠も使わない。数値・評価・選択の表は `compareTable`。定性のマトリクスは表にせず、`points` か図にする（`blockTable` は使わない。決まり20）。`addTable` は使わない（決まり17）
2. ミニ目次は既定では出さない（`miniNav: true` で出す）。出すのは、章立てのある長い報告・発表だけ。章のない資料、動画上映が中心の資料には付けない
3. ページ全体の結論を下に置かない。置いてよいのは、左右に並べて比べるパネルの、それぞれの結び一文だけ
4. タイトルは、いまどの話かの項目名だけ。主張はリードの最初の文に置く（2026-11-24 に「テーマ：短い要点」から改めた）
5. 左右2ペインは、同じ観点で2つを比べるページだけ（今と見直し後、実際と計画など）。文章・事実の列挙は1列
6. 構成案の値には出典を付けない。追加調査で外から持ち込んだ数値のページだけ、`source` で1行（調査名と年）を置く。URL は台帳に持つ
7. 表紙はタイトルと日付だけ。経営会議用の報告書だけ副題と所属を足す。ピッチは、何の事業かを一言で言う副題を足してよい
8. 色は、題材に合わせて資料ごとに決める（決まり13。`createDeck` の `theme`）。役割は固定：文字＝`ink`、強調＝`emph`、問題＝`accent`（赤）、退かせる＝灰（`references/tokens.md`）

| 全体に占める割合（シェア・構成比） | `pieChart`（円・ドーナツ。主役の区分だけ強調の色、合計は円の中）。形の割り当てで「比べる」に横棒を使っていても、割合は別の意味なので円 | 横棒にシェアを並べる、合計（上位◯社の計）を内訳と同じ棒に並べる（部品が警告） |
| ビジネスモデル・仕組みの図 | `bizModel`・`processFlow` だけで描き、図の外に説明の文の塊や凡例を置かない。矢印・箱の名前で読めるようにする。お金の内訳のように図に入らない話は、別のページにする（持ち帰る1つを図の横に大きく置くのはよい） | 図の横に小さな文の塊（内訳・注記）を足す、印の凡例を置く |
| リスクと手当て | 独立したページで、リスク → 手当ての対を左右に並べる。前のページの計画の図に重ねない（`echo`・`series` にしない） | 計画の図を薄く敷いて、上にリスクの箱を重ねる |
| 決裁の依頼 | 決める額と、その内訳（費目ごとの棒か表）、決めた後の次の一歩（いつ・誰が・何を）を、そのページの主役の図にする。決める額は `focusValue`。1ページで決めてもらうのは1件。根拠の計画の図をもう一度見せたいときは、`series`・`echo` で背面に敷いてよいが、前面の箱で背面の図の段階や文字を隠さない（箱は空きに置く）。内訳と次の一歩を、箱の中の小さな文やノートに回さない（2026-11-25 に改めた。前は「根拠の図を背面に敷き、決める段階だけ残し、前面の箱で言う」だったが、決裁のページが計画の図に見え、内訳が隠れた） | 計画の図を薄く敷いて箱で一部を隠す、内訳と次の一歩をノートに回す、太字の箇条書き2行だけ、`decisionPage` の文のマス目（警告が出る） |
| 新しい事業・製品のコンセプト（初めて見せる） | `concept`：価値を言う一文を中央に。価値の差が1つの物差しで言えるなら `contrast` で比べる相手と自社を同じ物差しに並べ、自社の行だけ強調。言えなければ一文だけ。仕組み・比べる表は次のページ（決まり24・25） | 誰に・何を・いくらでの属性の箱を並べる、1枚に名前・肝の流れ・他社との比較・示唆を詰める、いきなり仕組みの図から入る |
| 要約 | `summary`（決めてほしいことを上に1つ、強調の枠と主役の値。下に根拠を2〜4個、見出し1つ＋値1つで並べ、線でつなぐ） | `points` で見出しと灰の補足の文を並べる（ただの羅列で、何をどう読むか分からない） |
| 事実・知見の列挙 | `bullets` で見出し＋箇条書き（1列） | 罫線のリスト、構成案に無い分類ラベル |
| 図の中の箱 | 薄い塗りの矩形（枠なし）。枠は強調・問題・空きのときだけ | すべての箱に細い枠 |
| 棒グラフの主役 | 主役の1本を濃紺で塗り、他は灰（`highlight.mode: "focus"`） | 灰の棒に細い紺枠、問題ではないのに赤枠 |

| 構成の推移 | `ribbonBars`（積み上げ棒を帯でつなぐ。区分名は右端の棒の横） | 凡例を別に置く、高さを100%にそろえて量を消す |
| 示唆・提言・申し送り | `points`（言い切りの要点＋根拠の1文。右に「根拠 P.n」） | 長文の箇条書き、要点と説明に同じ黒丸 |
| 数値の図の見出し | `figHead`（何の数値か・単位・時点を左上に。系列の名前は凡例にせず、図の中の示すものの近くに） | ページごとに位置が違う、図の下に注記 |
| 数値のグラフ全般 | `references/charts.md` の対応表で選ぶ（円・ドーナツ、折れ線、積み上げ、マリメッコ、ブリッジ、散布図、ヒートマップ、KPIタイルなど）。主役だけ濃紺、名前は線や区分の横に直接、目盛り線は使わない。折れ線は3本まで（4本以上は警告。推計は幅の帯にする） | 凡例に頼る、目盛り線と値の二重、2軸の複合グラフ |

論旨に必要な情報は足す。それ以外の構成案に無い要素（分類ラベル、補足、ミニ目次、アイコン）は自分で足さず、足したほうが良いと思ったら提案する。

## 強調と文字

- 見る所を宣言する。`base` の `focus` に、最初に目が行くべき要素（持ち帰る1つ）を書き、強調はそこにだけ置く。表の列や行の丸ごとは見る所にならない（決め手のセル1つを `focus: true`）
- 強調は1ページ1か所。濃い塗り（E3EAF4）、ink 2pt の枠、文字を1〜2pt上げる、を同じ1か所に重ねるのは可（塗りだけでは目に入らないことが多い）。別の場所に別の強調を足さない。問題の所は赤枠と赤字で、あるべき側の強調と対にする
- 主役を一番大きく・太く・濃く。リードを読まずに3秒見て一番目立つものが、リードの主張と同じであること
- 太さは bold と regular だけ。図の中の文字サイズは4段まで
- 図の中の文字は soft（4A5568）以上・18pt 以上（密な図だけ 16pt）。gray は線と図形にだけ使い、文字には使わない（22）
- 濃紺の塗りは「データの印」と「飾りの面」で分ける。データの印（棒・面・点・線、ガントの帯、人のピクト）は濃紺で塗ってよく、単系列の棒は主役の1本を濃紺（ink）、他を灰（`C.bar`）にするのが既定の強調（`barChart` の `highlight.mode: "focus"`）。飾りの面（見出しブロック、ラベル、矢羽、パネル、カード、文字を載せる箱）は濃紺で塗らない。白抜き文字は、紺地の区切りページ、番号丸、濃紺のデータの印の中だけ
- 強調の色: 問題ではない主役＝濃紺、問題・視線誘導＝赤。問題ではない主役を赤枠で示さない
- 強調の数え方: グラフでは、系列を丸ごと強調の色で塗らない。比べる2系列は濃い灰と薄い灰にし、強調の色は見る所の棒・点だけ（23）。単系列で主役を濃紺にする本数は、リードが名指しした数と同じにする（「最多は30代、0〜9歳も多い」なら2本）。リードが名指ししていない棒を濃紺にしない
- 値を棒に添える: 主役の値は 36pt bold（`FOCUS_FS`）、他の値は 19〜20pt soft（色や枠だけでなく、大きさで示す。決まり16）。値を出したら縦軸と目盛り線は置かない
- 色・記号・線種には、それぞれ説明できる意味を持たせる

## 同じデータ・議題を複数ページで扱うとき

1つの図で2つ以上を言うときも、この節のやり方で分ける。`series`（`references/components.md`）を使えば、下の 1〜4 を部品がやる。

1つのデータや議題に複数ページで触れるときは、新しい図を起こさず、同じ図を背面に敷いて前面に言いたいことを重ねる。めくっても図が動かず、変わった所（前面の要素）だけが目に入る。

1. 1枚目は図だけで事実を見せる（主役の強調はしてよい）
2. 2枚目以降は、同じ図を同じ関数・同じ引数で描き、`echo` で白く薄くする。位置・大きさ・縦軸の最大・色を変えない。縮めたり下にずらしたりしない
3. 前面に、そのページで言うことを `messageBox`（分かったこと・結論）か `callout`（番号つきの論点、問題）で置き、赤の線で指す要素を示す。範囲を指すときは `toRange`。根拠が別のページにあるなら `refKey` で「P.n」を添える
4. 前面で指す要素（主役の棒、値のラベル）は、`echo` の `keep` で覆いの上に元の濃さで描き直す。薄いままにしない
5. 前面の要素を置く空きが無いときは、1枚目の段階で縦軸の上限を上げたり、図の下に余白を残したりして、両ページ同じ寸法にしておく（ガントは `compact`）。この空きは、1枚目で点検項目19（大きな空き）の例外にしてよい。大きさは前面の箱1つ分（本文の高さの4分の1程度）まで
6. 図の位置・データ・座標は定数にして両ページから同じものを渡す。確かめるときは、2枚目を `echo(..., { check: true })` にして画像を作り、`python3 <skills>/pptx-deck-design/scripts/figure_diff.py <1枚目.jpg> <確認用.jpg>` で図の領域の差が 0 であることを見る。確かめたら `check` を外す

関数で描けない図（画像として貼った図など）も、同じ画像を同じ位置に貼って薄くする。

## 引き算と、その逆

削るもの（ページ下の注記、図の補記、番号での離れた対応づけ、副題、自明なラベル、意味のない記号、目的外の情報）と、削りすぎて差し戻された状態（論理の飛躍、前提なしの図、スカスカ）は `references/subtraction.md`。「シンプルに」と言われたら、情報量は保って装飾を減らす。ページ間で図・名称・区分色・読む向きをそろえるルールも同じファイルにある。
